## GAP (inconsistent — reported, not fixed)

The one-step rollout does NOT move either candidate's belief, and the reason
is a carrier mismatch: **the declared source's pattern tokens are bare
keywords** (`:admission/task-stated`, `:repair/verified-dated-recheck`) —
the same style as the existing mission source files — **while q0 carries
target-qualified pairs**. The kernel's guard check
(`cascade_model_manifest.clj:112-116 guard-holds?`, `set/subset?` of
`:present` against the state) tests bare tokens against pair-carrying
states, so no guard ever holds, no pattern fires, and both candidates'
predicted beliefs are identical — which would make ⟨1⟩3's discrimination
impossible.

Evidence that the live machine elsewhere uses qualified pattern tokens: the
click-1..3 ledgers' precision-family candidates carry
`:produces #{["M-aif-policy-conditioned-eig" :hole/h6378c65a4012]}` —
pairs — although the declared source files' `:patterns` are bare. So a
qualification step exists somewhere between `load-declared` and live scoring
that I did NOT find in `cascade-sources`, `cascade-problems`,
`cascade-policy` (`token-interpretation` :210-229 adapts shape but does not
qualify tokens), or `cascade-observation-scoring`. Exactly one of the
following is true and must be settled before ⟨1⟩3's CHECK:

1. the live tick qualifies declared-source tokens with the target at state
   assembly (in `full_loop_runner`'s state construction, not traced within
   this handoff's read-only budget) — then my one-off missed the wiring and
   the live q0+patterns agree; or
2. no such qualifier exists for the declared-source path — then the frozen
   reference input as published cannot discriminate, and the fix (qualify
   the source's tokens, or qualify at load) belongs to the next sub-step,
   not to this discovery.

What is NOT in doubt: q0 itself (the receipt construction is unambiguous,
recomputed above), A = identity at zero rates, and the fact that rollout and
scoring read one shared `:cascade-belief` state slot.
