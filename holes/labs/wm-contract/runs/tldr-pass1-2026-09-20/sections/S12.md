## 1. IDENTIFY

### Motivation

`M-vsatarcs-writer` shipped the per-cycle writer-capability apparatus and demonstrated end-to-end via Option B live cycle 2026-05-20 (`:story-update` against `leaf-6-4-1.md`; full propose → predict → consent → execute → observe → trace cycle; prediction-error 0.0). `M-self-documenting-stack` (POC) ships LC1 — the operator-facing mission-search affordance that resolves the *discoverability* sub-shape of stack-self-documentation.

**This mission addresses the other sub-shape**: *autonomous-maintenance-loop*. The per-cycle apparatus works; the operator currently has to NOTICE drift and STEP the cycle. The goal: stack-self-detected drift; stack-self-resolved cycles; operator-stated invariants + operator-observed outcomes; no operator-in-the-loop at action-construction time.

Joe's framing 2026-05-20 (preserved verbatim from the predecessor):
> *"Right now we 'stepped' Option B, but in the future we're going to want it to run fully autonomously. ... The 'writer-capability' should ultimately allow me to put in place an invariant like 'Documentation is always up to date' and then not have to worry about it."*

**Two structural gaps** between the per-cycle apparatus and an autonomous loop (both deferred by M-self-documenting-stack POC; this mission resolves them):

1. **No drift detector**: WM doesn't observe "documentation freshness" as a channel. R2 currently has `loop-health`, `mission-health`, `sorry-count-norm`, etc. — but nothing measuring per-(canonical-source, dependent-documentation) staleness.
2. **No peripheral boundary + no delegation mechanism**: writer-capability is a set of elisp modules with no explicit boundary; any agent can use them or none. WM itself doesn't dispatch fresh agents to do scope-bounded writer-work.

### Theoretical anchoring

Inherits the framing from M-self-documenting-stack §1.2 ("Theoretical anchoring"). Specifically:

- **Active Inference (AIF+) at the meta-level**: WM's belief over the world includes documentation-freshness; observations update belief; EFE composes drift-resolution-actions; policy selects + delegates. The autonomous-loop is itself an AIF cycle, with action-class being "delegate a writer-agent to fix drift X" rather than "do work directly."
- **Peripheral spec (`~/code/futon3/docs/peripheral-spec.md` + `~/code/futon3c/`)**: capability envelopes; `vsatarcs-write` declares tools = writer-action-class constructors + consent-gate; scope = documentation files only.
- **Scope-bounded handoff (`~/code/futon3/library/realtime/`)**: dispatch task to fresh agent with bounded scope; observe completion; integrate result.
- **Invariants I-1 / I-2 / I-3 (futon3c CLAUDE.md)**: one agent = one session = one identity (auto-register fresh per-cycle); transport routes (does not create) (Agency `whistle` routes; doesn't impersonate); peripherals are inhabited (not delegated) (the fresh agent IS the writer; doesn't sub-delegate).
- **Consent-gate substitutability (M-vsatarcs-writer D1 + claude-4 v0.5.22 safety-property)**: autonomous-mode = consent-source-swap from `:operator` to `:autopen`; admissibility predicate = recursion-safety. Production-scale exercise of D1.
- **Shape-first IDENTIFY**: this mission is the **second** instance of `stack-self-documentation` shape (first being LC1 in M-self-documenting-stack). Specifically: the *autonomous-maintenance-loop* sub-shape applied to chain-link `code/source → docs`. Future siblings (test-freshness; sorry-resolution; bilateral-evidence pairing; mission-scaffold ↔ closure sync; patterns → missions cross-reference) inherit BOTH this mission's autonomous-loop mechanism AND M-self-documenting-stack's discoverability mechanism per their needs.

### Carried-forward tensions

Inherits all seven carried-forward tensions from the predecessor M-self-documenting-stack draft that apply to A+B (8/9/10 were LC1-specific and don't apply here):

1. **Where does the invariant live (registry-wise)?** A stored predicate that WM consults each tick. Where's the canonical home — futon2 (WM-internal), futon3c (Agency-adjacent), or a new dedicated registry? *Carry to DERIVE.*
2. **How is the "fresh agent" briefed?** The scoped prompt for the dispatched writer-agent needs: target file; proposed action shape; consent-source (autopen by default); exit criterion. Format TBD. *Carry to DERIVE.*
3. **What's the drift-tolerance schema?** Is it global (one staleness threshold) or per-(source, doc) pair (some docs tolerate more lag than others)? Operator-configured by default but the schema needs to exist. *Carry to DERIVE.*
4. **Rate-limiting + backoff.** If a drift signal stays high after a delegated cycle, what prevents WM from re-dispatching infinitely? Probably the admissibility predicate (per claude-4 v0.5.22) catches duplicate proposals, but the more general retry policy needs articulation. *Carry to DERIVE / VERIFY.*
5. **Agent identity reuse.** Each cycle registers a fresh agent (per I-1 + the agents/auto endpoint's ghost-reclamation). Does this fragment the bilateral-evidence record by author-id? The writer-event-id naming convention may need extension. *Carry to ARGUE / coordinate with claude-4.*
6. **Failure modes.** Network partition; Agency unavailable; agent registration fails; peripheral entry fails; writer-action fails mid-cycle. Each needs a recovery story. *Carry to DERIVE / VERIFY.*
7. **The "different way to enter the loop" Joe flagged.** Event-triggered vs continuous-EFE-composition vs time-triggered: this mission needs to commit to a primary entry-point pattern. Current proposal (event-triggered → continuous, with R10 heartbeat as fallback) needs validation. *Carry to DERIVE.*

New tensions from claude-4's v0.5.27 closure bundle (2026-05-20):

8. **Queue enumeration sources** (claude-4-named for the in-vivo cycle): *lifting-queue + mission-checkpoint queue + revision-entry queue*. Where exactly do these queues live? `lifting-queue` is presumably stories not yet rendered as chrome; `mission-checkpoint queue` is checkpoints with closure evidence not yet sync'd to scaffold; `revision-entry queue` is `.aif.edn` files awaiting new `:rev` entries. The three need canonical homes (in-memory? on-disk? regenerated each tick?). *Carry to DERIVE.*
9. **R7 in-vivo calibration mechanics**: R7's adaptive precision (claude-4-side) is exercised on reader-side observations; writer-side prediction-error histories need their own precision tracking. Shared infrastructure or parallel? *Carry to DERIVE.*
10. **`:G-pragmatic + :G-epistemic` weight ownership**: claude-4 ships per-class pragmatic helpers + recency-via-mtime epistemic. Where does the λ-weight live (the multiplier on each term)? Per-class? Per-mission? Global? Calibration target for L4b. *Carry to DERIVE.*

This mission inherits the discipline — should L1b ship with failing tests encoding the cross-side delegation (B2) spec, to be flipped when L4 lands? *Carry to VERIFY.*
