## 1. IDENTIFY

### Motivation

`M-vsatarcs-writer` shipped the *per-cycle* writer-capability apparatus (L3 + L4 + L4+ for `:mission-doc-sync` / `:aif-edn-revision-entry` / `:story-update`). The first Option B live cycle (2026-05-20) demonstrated that the apparatus can resolve a documentation gap end-to-end via the consent-gate's `:autopen` source with operator-via-CLI ack as the consent-equivalent. **But each cycle is operator-stepped** — claude-2 noticed the gap, constructed the action, ran the cycle. There's no autonomous detection-and-resolution loop.

Joe's framing 2026-05-20: *"Right now we 'stepped' Option B, but in the future we're going to want it to run fully autonomously. ... The 'writer-capability' should ultimately allow me to put in place an invariant like 'Documentation is always up to date' and then not have to worry about it."*

**Broader framing — the deeply-self-documenting-stack goal** (Joe 2026-05-20):
> *"I want the futon stack to be deeply self-documenting — patterns → missions → code → docs or something like that (different or reduced chains are possible). It is OK if we only do part of that now. But hopefully there are other missions out there that we can link to even in the IDENTIFY stage that will make the context of this mission meaningful. Which brings me to another gap: I don't remember how many missions there are out there — lots — and as I mentioned, I don't like mission proliferation any more than you like scope creep! A good solution would be a search box where I could start typing 'self documenting stack' and get a summary of the relevant missions..."*

The "deeply self-documenting" goal is the chain: `patterns → missions → code → docs`. Each transition in the chain can drift. This mission ships the **mechanism** for autonomous drift-resolution + **two instances** of its application (one chain-link being maintained: code/source → docs; one chain-link being made navigable: missions → operator-searchable-index).

**Two discrepancies between ideal and actual:**
- *Doc-freshness*: invariant should be operator-stated; stack maintains it; currently each cycle requires operator-in-loop at action-construction time.

**The discrepancy between ideal and actual:**
- *Ideal*: Joe states an invariant ("documentation is always up to date"); the stack maintains it without further operator involvement
- *Actual*: each documentation-update cycle requires an operator-in-the-loop at action-construction time (deciding "this leaf needs updating because of this scoop"); the writer-capability resolves the cycle once started, but doesn't start cycles itself

**Two structural gaps** between the per-cycle apparatus and an autonomous loop:

1. **No drift detector**: WM doesn't observe "documentation freshness" as a channel. R2 has `loop-health`, `mission-health`, `sorry-count-norm`, etc. — but nothing measuring per-(canonical-source, dependent-documentation) staleness.
2. **No peripheral boundary + no delegation mechanism**: writer-capability is a set of elisp modules with no explicit boundary; any agent can use them or none. WM itself doesn't dispatch fresh agents to do scope-bounded writer-work.

Closing these two gaps is what this mission is for.

### Theoretical anchoring

- **Active Inference (AIF+)** at the meta-level: WM's belief over the world includes documentation-freshness; observations update belief; EFE composes drift-resolution-actions; policy selects + delegates. The autonomous-doc-maintenance loop is *itself* an AIF cycle, with the action-class being "delegate a writer-agent to fix drift X" rather than "do work directly."
- **Peripheral spec (`~/code/futon3/docs/peripheral-spec.md` + `~/code/futon3c/` patterns)**: capability envelopes constrain what an agent can do within a scoped task. A `vsatarcs-write` peripheral declares: tools = writer-action-class constructors + consent-gate; scope = documentation files only; entry/exit conditions explicit.
- **Scope-bounded handoff (`~/code/futon3/library/realtime/`)**: pattern for "dispatch task to fresh agent with bounded scope, observe completion, integrate result." Directly applicable to WM-delegates-writer-work.
- **Invariants I-1 / I-2 / I-3 (futon3c CLAUDE.md)**: one agent = one session = one identity; transport routes (does not create); peripherals inhabited (not delegated). The fresh-agent-into-peripheral pattern complies: a new agent is *registered* (not impersonated by an existing one); transport (Agency) routes the whistle; the agent *inhabits* the peripheral.
- **Consent-gate substitutability (M-vsatarcs-writer D1, claude-4 v0.5.22 safety-property generalisation)**: the autonomous loop is *exactly* the consent-source-swap from `:operator` to `:autopen`. The substitutability promise gets its first production-scale exercise here. The admissibility-predicate-as-recursion-safety property prevents runaway.
- **Shape-first IDENTIFY (extended for the squeeze-in)**: this mission's gap is **two instances** of a **stack-self-documentation** shape — the per-application sub-shape is **autonomous-maintenance-loop** for some applications (drift-detect → propose → delegate → resolve) and **discoverability surface** for others (index → search → summarise). The two share the underlying assertion: *the stack must know about itself well enough to surface that knowledge*.

  **Application instances at chain-links** (patterns → missions → code → docs):
  1. *Code → docs freshness* — autonomous-maintenance-loop on (canonical-source, documentation) pairs. **In scope; Deliverable B target.**
  2. *Missions → operator searchability* — discoverability surface over the 78-mission corpus. **In scope; Deliverable C target (squeezed in per Joe 2026-05-20).**
  3. *Patterns → mission cross-reference* — discoverability surface over the 853+ flexiarg pattern library, mapped to missions that apply them. **Deferred.**
  4. *Code → tests freshness* — autonomous-maintenance-loop on test coverage. **Deferred.**
  5. *Sorries → autonomous resolution* — autonomous-maintenance-loop on the sorry queue. **Deferred (overlaps M-a-sorry-enterprise).**
  6. *Bilateral-evidence auto-pairing* — autonomous-maintenance-loop on cross-side closure correspondences. **Deferred.**
  7. *Mission scaffold ↔ .aif.edn closure sync* — autonomous-maintenance-loop on commitment vs accomplishment. **Deferred (overlaps already-shipped `:mission-doc-sync` action-class but at maintenance scope).**

  Naming the shape lets future siblings inherit the pattern; this mission delivers **two** instances (one of each sub-shape) and prototypes shared mechanism. The two-instance ship is deliberate: it stress-tests the abstraction (would a single-instance mission risk under-generalising?), and it directly answers Joe's "deeply self-documenting" framing in proportion to what's tractable now.
