# H-PUBLISH-D — why publication refuses, per refused id

Discovery packet for PROOF-2a hole **H-publish** ("carry the repair id and
resolution context through to publication, so a close never refuses to
publish an obligation the machine itself produced"). Discovery only; no
fix, no dismissal, no store writes.

Record under study: `data/wm-runs/tick-run-record-2026-09-24-1790225596.edn`
(click 2, 2026-09-24T04:53Z), `[:repair/publication]`: **68 entries, all
`{:status :publication-refused :reason :resolution-context-unavailable}`**.
No other refusal reason occurs. Every entry carries `:store/status
:resolved` — the resolutions exist and are resolved; publication, not
resolution, is what refuses.

## Mechanism (from the code)

1. At tick start the runner calls `discharge-receipt/catch-up!`
   (`full_loop_runner.clj` ~5588), which enumerates **every** id in
   `data/wm-repair-obligations/resolutions/`
   (`repair/discharge-resolution-ids`) and attempts
   `publication-result!` → `publish!` → `derive` on each. The store has
   exactly 68 resolutions, so the 68 refusals are the whole population,
   re-derived and re-refused at every tick.
2. `derive` (`repair_discharge_receipt.clj` ~18-48) reconstructs the
   receipt exclusively from three immutable store records — findings/,
   implementations/, resolutions/ — and refuses, in order:
   - `:resolution-not-successful` if the resolution's `:repair/status` is
     not `:resolved` (never fires here: all 68 are `:resolved`);
   - **`:resolution-context-unavailable`** if
     `(:repair/discharge-context resolution)` **or**
     `(:repair/discharge-context implementation)` is nil — this is the
     refusal on all 68 entries;
   - `:resolution-binding-invalid` if the two contexts and the
     `:successor-relation` do not mutually bind (ids, attempt ids, commit,
     witness, intent hash, attempt distinctness).
   The namespace docstring states the policy: *"Legacy resolutions without
   the retained context refuse explicitly; missing provenance is never
   invented."*
3. The context is written by exactly one pipeline:
   `repair_discharge.clj finalize!` (~117-183), invoked from the runner's
   close path (`full_loop_runner.clj` ~4351 `finalize-run!`). It builds a
   `{:schema :wm/repair-discharge-context-v1 ...}` value — phase, repair
   id, durable grounded `:close` `{:attempt/id :run/id :closed-at
   :grounded? :close-snapshot}`, `:artifact`, `:artifact-binding`,
   `:review-job`, `:review-evidence`, `:witness`, `:producer`, and a
   **retained `:intent` snapshot** (`retain-intent!` writes a
   `discharge-operations/` record and pins its `:path`/`:sha256`/
   `:edn-text`) — and passes it into `repair/record-implementation!`
   (phase `:implementation`) or, on a later distinct successor close, into
   `repair/successor-resolution!` → `repair/resolve!` (phase
   `:successor-validation`).
4. The writers make the context **optional**: `record-implementation!`
   (~1660-1730) and `resolve!` (~1764-1832) assoc it under `(cond-> ...
   context)`, and `discharge-context!` (~1649) validates it only when
   present. A nil context writes a record that can never publish, and
   nothing refuses at write time.

## What was unavailable, per refused id

Store census (2026-09-24, read-only): **all 68 resolutions lack
`:repair/discharge-context`; 15 of the 68 also have no
`implementations/<id>.edn` at all.** No id was nil or malformed (all pass
`safe-id!`'s charset); no resolution has a partial context with one key
missing — the key is wholly absent in every case. The 9 records in
`discharge-operations/` are all `:kind :outcome` receipts of failed
`finalize!` runs (nil repair id → `:unsafe-repair-id` at `:binding`);
**no `:intent` retention exists for any of the 68 ids.**

Three classes account for the population:

- **A — legacy (44 ids):** resolutions written 2026-07-14 → 2026-09-21,
  before or beside the context schema introduced in commit `3bdd226a`
  (2026-09-21, "Add witnessed two-phase runner discharge and recoverable
  receipt publication"). Implementation records exist (where present) but
  also lack the context. The closes, review jobs and witnesses these
  resolutions summarize were never captured in the context shape, and the
  retained `:intent` snapshot does not exist.
- **B — late script (9 ids):** resolutions written **2026-09-24T04:04Z**
  — after the schema existed — by the authorized lab script
  `holes/labs/wm-contract/runs/stop-line-discharge-2026-09-24/discharge.clj`,
  which calls `repair/successor-resolution!` with `:resolve-fn
  repair/resolve!` and bare `repair/resolve!`, passing **no**
  `:repair/discharge-context`. The writers accepted the nil context
  (mechanism 4 above). These are machine-produced obligations resolved
  through an authorized writer that the context contract does not reach.
- **C — no implementation record (15 ids):** `derive` requires
  `(:repair/phase implementation)` = `:implementation` and the
  implementation's context; with no implementations/ record at all,
  derivation is impossible regardless of any amendment to the resolution
  side. One of these (`repair-ea1-6a0de60a...`) has a resolution of a
  different schema entirely (`:wm/historical-repair-resolution-v2`,
  written 2026-09-12).

## What "carry the repair id and resolution context through" concretely means (proposed amendment)

For `derive` to publish, the store must hold, per id:

1. `implementations/<id>.edn` with `:repair/phase :implementation` and
   `:repair/discharge-context {:schema :wm/repair-discharge-context-v1
   :phase :implementation :repair/id <id> :close {:attempt/id :run/id
   :closed-at :grounded? true :close-snapshot} :artifact
   :artifact-binding :review-job :review-evidence :witness :producer
   :intent {:path :sha256 :edn-text}}`, where `:intent` pins a
   `discharge-operations/` record of `:kind :intent` written by
   `retain-intent!` at implementation time, and `[:close :attempt/id]`
   equals the record's `:implementation-attempt`.
2. `resolutions/<id>.edn` with `:repair/status :resolved`, `:repair/phase

   :successor-validation` (`[:close :attempt/id]` = `:validation-attempt`
   = the relation's `:successor-attempt/id`), and a
   `:successor-relation` whose repair/successor attempts, runs, commit and
   witness-ref/sha256 match both contexts — repair and successor attempts
   and runs distinct.
3. The only pipeline that produces all of this is
   `repair-discharge/finalize!`, reached from a click's close in
   `full_loop_runner.clj`. "Carrying through" therefore means: **the
   close that implements a machine repair and the later close that
   validates its successor must each hand their durable close, review job,
   witness and retained intent to the store transition they author.**

The amendment, stated as a definition change:

- **A1 (required carrier):** make the context mandatory at write time.
  `discharge-context!` currently validates the context only when present;
  `record-implementation!` and `resolve!` assoc it only when present.
  Change: a store transition to `implementations/` or `resolutions/`
  without a valid `:repair/discharge-context` refuses
  `:discharge-context-missing`. Effect: a resolution that can never
  publish can never be written; the class-B failure (authorized writer
  producing an unpublishable resolution three hours before the click that
  then refused it) becomes impossible at the writer, not permanent at the
  reader. Callers that today pass no context (the two lab discharge
  scripts) must either run through `finalize!` or supply a context that
  passes `discharge-context!`'s binding checks.
- **A2 (legacy disposition, typed, no fabrication):** the 68 existing
  resolutions cannot acquire a context honestly — the retained `:intent`
  snapshot does not exist and re-deriving contexts from cohort records
  would be exactly the fabricated provenance the falsifier below forbids.
  Give them a typed terminal disposition: either dismissal through the
  existing dismissal path (`repair/dismiss-repaired-elsewhere!` family,
  where its contract applies) or a new `:publication-unreachable` marker
  record (one per id, written once, naming this packet) that `catch-up!`
  reads and reports as `:status :publication-unreachable` instead of
  re-deriving and re-refusing forever. Absence stays typed; nothing is
  substituted. Under current definitions **all 68 ids are
  machine-unpublishable** — class C outright (no implementation record can
  ever exist with a context binding a close that was never captured),
  classes A and B because the context is unrecoverable — so all 68 are
  dismissal candidates. This packet dismisses nothing.

## Falsifier, restated as a bad case

H-publish fails if a close can publish with a fabricated context. The
negative case any change must preserve: a `resolutions/<id>.edn` carrying
a `:repair/discharge-context` whose bindings do not all hold — wrong
`:repair/id`, `[:close :attempt/id]` unequal to the relation's
`:successor-attempt/id`, `:replacement-commit` unequal to the relation's
`:repair-commit`, `:witness` unequal to the resolution's, intent
`:sha256` unequal to `sha256(:edn-text)`, the intent's embedded witness
unequal to the context's, or repair/successor attempt or run ids equal —
must make `derive` refuse `:resolution-binding-invalid`, and `verify!`
must refuse `:receipt-store-mismatch` / `:receipt-record-hash-mismatch`
when any embedded store byte differs. Symmetrically, adding a context to
an existing legacy record by rewriting it must be impossible through the
store writers: records are immutable (`write-new!` only,
`capture-under!` pins bytes), so a fabricated retrofit cannot enter
through `record-implementation!`/`resolve!` at all — it would have to be
written by hand outside the writers, which is exactly what A2's typed
marker exists to make unnecessary.
