## 1. The mismatch, restated with its pointers

`control-stages.edn` gives the R16 box the label **"Grounded actuation"**. The
one control edge leaving that box reads **"observe construction"**
(`control-map-edges.edn:23`), relabelled on 2026-08-31 because the old label
`re-observe` asserted an outward act the code does not perform. The box and its
outgoing edge therefore disagree, and the box is the side that agrees with
nothing: the code that runs the node says the opposite of "grounded actuation"
in its own words —

- `futon2/src/futon2/aif/enact.clj:12-15`: "ENACTMENT IS ARTIFACT-ONLY
  (read-only in `apply-cascade!`'s sense) … NO substrate write, NO outward
  action";
- `futon2/src/futon2/aif/enact.clj:130-133`: `engine-wiring` "Returns a typed
  result: `:constructed-wiring`, `:no-construction`, or `:enactment-failed`" —
  an in-model construction, not an act.

C485 §3 found this and C485 §6 item 2 named the repair: "Give
`control-stages.edn:20` a dated amendment in the same shape the edge got."
C485 §5 typed it "not repaired, **not blocked**".

## 2. Where the label actually lives — three files up, in another paper

`control-stages.edn` is generated (`control-stages.edn:1`, "GENERATED by
empirics-futon/gen_control_stages.py -- do not edit (WR-8)"), so the label is
not stored there. Following it back:

| layer | file:line | who writes it |
|---|---|---|
| generated registry | `control-stages.edn:24` | `gen_control_stages.py` |
| drawing it reads | `p4ng/aif-control-map-futon.svg:155` | `gen_wr_overlay.bb` |
| base drawing that generates from | `p4ng/aif-control-map-paper.svg:173` | drawn by hand |

`gen_wr_overlay.bb:3-6` states the rule for the last hop: it "Reads
`aif-control-map-paper.svg` (**UNMODIFIED**) … The base drawing is never edited
(WR-8): it stays the companion paper's artifact and this is a derived third
channel over it."

So there is no site inside this repo's derived layer at which the R16 box label
can be corrected. The only site is the plop-2026 companion paper's drawing,
which the generator that consumes it declares off-limits.

## 4. What was built: a typed amendment the drawing can invalidate

The registry no longer carries the contradicted label silently.
`gen_control_stages.py` gained a node-label amendment channel, fed by
`p4ng/empirics-futon/control-stage-amendments.json`, emitting
`:label-amendment` on the node's row (`control-stages.edn:25-34`). The shape
follows the edge's `:label-amendment` (`control-map-edges.edn:24-30`), with
`:drawn-label` in place of `:old-label` because **nothing here renames
anything** — the amendment records a disagreement, it does not resolve one.

The reason an amendment is worth having is that it can go stale, so the
generator refuses one that has:

- `:node` absent from the drawing → exit 1 naming the node;
- `:drawn-label` that is no longer what the drawing says → exit 1 naming both
  labels. This is the case that matters: the day Joe corrects the box, the
  amendment becomes a report of a settled disagreement, and the generator stops
  rather than emits it;
- a missing field, a duplicate node, or a quote/backslash in a value → exit 1.

Controls on every publish (`negative_controls.sh` 7a–7c): 7a plants the
correction itself into a **copy** of the drawing (renaming the box to
"Artifact-only enactment") and requires the refusal, naming the stale label;
7b points the amendment at an undrawn `R99` and requires the refusal naming it;
7c is the positive control — the drawing and the amendments as they stand
render, the amendment lands on R16 with its typed `:status`, and the emitted
file is byte-identical to the committed `control-stages.edn`, so a hand-edit of
the generated registry fails here.

Verified live rather than assumed: with the `:drawn-label` assertion disabled,
7a fails ("control-stages merged an amendment for a label the drawing no longer
carries"); restored, the suite passes 26 negative / 13 positive.

## 5. Found while following the label: Figure 5 still prints `re-observe`

Not acted on, and this is the one thing in this record that is new work rather
than a disposition.

`aif-control-map-futon.svg` is generated from the base drawing by
`gen_wr_overlay.bb`, and it **has not been regenerated since 2026-08-25**
(`3e375d5`), while the base moved twice on 2026-08-31. So the file the paper
includes at `sec-operator.tex:64` — Figure 5, the war-room overlay — still
draws the withdrawn label:

- committed `aif-control-map-futon.svg:69`: `re-observe`
- base `aif-control-map-paper.svg:73`: `observe construction`

Re-running the generator also brings in `0598d19`'s measured-route layer, the
`R3a` and `TRACE` boxes and a legend entry.

**Why this is not repaired here, and it is not a scope preference.**
Regeneration is not mechanical: run `gen_control_stages.py` against the
regenerated drawing and it refuses —

```
AssertionError: ambiguous stage assignment: a node sits 79px from its header
```

— because `BOX_W` is hard-coded at 140 (`gen_control_stages.py:38`) while the
new `R3a` and `TRACE` boxes are 70 wide, so their centres are computed 35px off;
and because a drawn `TRACE` box collides with the `TRACE` row
`EXTERNAL_MEMBERS` adds on the stated grounds that TRACE is "absent from …
the SVG's R-node boxes", which `0598d19` made false. Fixing that changes the
node population of `control-stages.edn` (19 → 20, with `R3a` new), which is an
input to both Figure 5A and Figure 5B. That is a generator change plus two
figure changes with its own acceptance.

**Which instance it belongs to.** Not this one. The claim is withdrawn at every
site that *authors* it, including the base drawing; what remains is one derived
render not re-run after its source moved — the artefact-boundary class, class 4,
where the tally already carries `:svg-fixed-pdf-stale` whose evidence names
`p4ng 0598d19` and claims "output reverified". That claim is what this finding
bears on. The counting rule fixes the 61-instance population, so this sharpens
an existing instance rather than minting one; re-typing that instance's status
would move the numbers `make_defect_tally_figure.py` prints, which is not U31's
to do. Carried to `CLEANUP-QUEUE.md` as a proposed row of its own, with its
shape written out — `PROPOSED-ROWS.md` is generated by `harvest_refusals.bb`
and says so at its head, so it is not a place to file by hand.
