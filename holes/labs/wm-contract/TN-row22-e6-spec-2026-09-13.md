## E6a: slow state influences approved selection and enactment

E6a is a forward, same-tick chain:

`slow state -> E5 exact shaped occurrence table -> R6 scoring/posterior ->`
`E2a approved occurrence domain -> selected exact occurrence -> E3 R9`
`pre-enact authorization -> E2b approved exact enactment`.

Carrying `:slow/mode` beside a decision is not evidence of influence. A passing
E6a witness needs a paired fixed-context comparison whose only changed input is
the independently declared slow-state/mode record. At least one shaped
prior/delta must differ and that difference must propagate through the retained
scoring inputs to a different selected and approved enacted occurrence. If the
selected occurrence is unchanged, the record is an honest no-change result and
does not qualify behavioral influence at that field.

### Pure verifier interface

Proposed public function:

```clojure
(verify-forward-influence
  {:mode :isolated-test|:production
   :authority-root <independently configured root>
   :sources
   {:fixed-context <pin>
    :slow-state-a <pin> :slow-state-b <pin>
    :e5-a <pin> :e5-b <pin>
    :r6-scoring-a <pin> :r6-scoring-b <pin>
    :e2a-a <pin> :e2a-b <pin>
    :selection-a <pin> :selection-b <pin>
    :e3-a <pin> :e3-b <pin>
    :e2b-enactment-a <pin> :e2b-enactment-b <pin>}})
```

Every pin resolves one strict UTF-8, single-EDN byte buffer and is checked
against an independently configured SHA-256 before parsing. Every record binds
`:model/id`, `:model/revision`, `:run/id`, `:tick/index`, `:cohort/id`,
`:event/id`, producer declaration/source SHA, full ordered
`:candidate/occurrence-id` domain and exact action bytes. The fixed-context
authority owns all fields other than the slow state and enumerates those bytes;
neither arm may supply its own context.

The verifier replays the reviewed E5 function for both arms, then joins every
shaped occurrence—not merely the winner—to the exact R6 scoring input. It
requires complete score/posterior coverage, the exact E2a approved domain,
selection from that domain, E3 authorization for the selected occurrence before
enactment, and E2b equality through the enactment record. E1/R11 costs,
utilities, budgets and accounting remain independently pinned; shaped posterior
mass must not be substituted for utility. The result reports the exact first
changed field and selected/enacted difference. It never searches for or clips
G, rewrites priors, or changes canonical equations.

### Required E6a rejection controls

1. Drop, duplicate or reorder a shaped occurrence at any downstream boundary.
2. Keep selected/enacted identity changed but borrow scoring or E2a bytes from
   the other arm.
3. Change score, selection or enactment while the shaped tables are identical.
4. Change extra fixed-context fields with slow mode; refuse confounding.
5. Change shaped values but retain the same selection: return non-qualifying
   `:no-behavioral-influence`, never success.
6. Select outside E2a approval, substitute first-passing enactment, or mutate
   action bytes.
7. Omit, stale, post-date, self-author, or cross-occurrence the E3/R9 verdict.
8. Present E2b post-event equality without the pre-enact E3 authorization.
9. Cross run/tick/model/cohort/event or source revision between any link.

### Missing runtime seam

There is no runtime composition from reviewed E5 shaping into the actual R6
scorer and onward through E2a/E3/E2b. The current `close-loop!` still chooses the
first passing gate. The later runtime packet must insert the reviewed shaped
table before scoring, retain the full chain, and make E3 authorization mandatory
immediately before exact E2b enactment. This specification does not authorize
that packet or treat isolated evidence as a firing.

## E6b: witnessed outcome at t updates slow state at t+1

E6b is feedback, not part of E6a's same-tick proof:

`independently witnessed terminal outcome for occurrence c at (run r,t) ->`
`exact prior slow-state revision -> one advance-slow-state application ->`
`persisted slow state at (r,t+1)`.

The outcome must name the exact E2b-enacted occurrence and action class, carry
independent outcome evidence, and be terminal `:succeeded` or `:failed`.
Abstained, missing, pending, indeterminate, enactment-failed, or unwitnessed
outcomes do not teach the slow state. They produce a typed refusal/absence, not
a failure observation.

### Pure verifier interface

```clojure
(verify-feedback
  {:mode :isolated-test|:production
   :authority-root <independently configured root>
   :sources
   {:transition-context <pin>
    :prior-slow-state <pin>
    :e2b-enactment <pin>
    :outcome-witness <pin>
    :application-ledger <pin>
    :claimed-next-slow-state <pin>}})
```

The independently owned transition context fixes run, source tick `t`,
destination tick `t+1`, exact occurrence/action, model revision, prior
slow-state revision, feedback event ID and expected source pins. The prior state
contains a nonempty stable revision and full intrinsic table. The outcome
witness binds the same occurrence/action/run/tick, its terminal status,
`:fast/action-class`, boolean success value, evidence artifact and independent
review/provenance. The claimed next state binds the destination tick and names
the prior revision and feedback event.

The verifier calls the pinned production `advance-slow-state` once with the
resolved prior, typed outcome and deterministic context. It compares the entire
claimed next state, including unchanged classes, updated alpha/beta, intrinsic
value, previous/new mode and feedback record. A successful result establishes
the declared update at those inputs; it does not establish a live caller.

Exactly-once identity is `(model revision, run, source tick, destination tick,
occurrence id, outcome-evidence id, prior-state revision, feedback-event id)`.
The independently retained application ledger must contain exactly one
committed application with matching input/output digests. Zero is
`:feedback-not-applied`; more than one is `:duplicate-feedback`; the same event
with different pins is `:feedback-conflict`. Replay returns the already committed
identical next state and never increments again. A new event cannot reuse the
same prior revision after another event has committed.

### Required E6b rejection controls

1. Missing, unwitnessed, nonterminal, abstained, enactment-failed or unknown
   outcome; success may never default false.
2. Outcome for another occurrence/action/action-class/run/tick/model.
3. Destination other than exactly `t+1`, same-tick feedback or a missing prior.
4. Stale prior revision, changed prior bytes, or next state naming another
   predecessor revision.
5. Duplicate ledger application, omitted application, reused event ID,
   conflicting input/output digests, or reordered ledger history.
6. Update more than the named action-class Beta entry; drop an unchanged class;
   increment by other than one; invert success/failure.
7. Mutate the derived mode, previous mode, update record or evidence reference.
8. Borrow a valid witness, prior, application receipt or next state from another
   transition.
9. Candidate-provided source paths, scope relabeling, malformed UTF-8,
   multi-form EDN or digest mutation.

### Missing runtime seam and ownership

`advance-slow-state` is pure and has no production caller/persistence join for
this edge. A later runtime packet needs an independently owned slow-state store
with compare-and-commit on prior revision plus an immutable application ledger;
it must run only after independently witnessed E2b terminal outcome retention
and before tick `t+1` reads slow state. The outcome producer cannot approve its
own evidence, and the state store cannot declare its own application ledger
complete. Recovery must replay committed events by stable identity, not repeat
the Beta increment.
